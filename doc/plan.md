# 掼蛋 AI 项目计划

> 依据 `prd.md` 与 OpenGuanDan 平台文档制定。
> 技术栈：**TypeScript** | 需要 **UI** | 周期：**约 1 周** | 团队：**3 人**

---

## 1. 项目目标（来自 PRD）

1. 基于比赛平台 [OpenGuanDan](https://github.com/GameAI-NJUPT/OpenGuanDan) 与示例代码，设计并实现掼蛋 AI；
2. 与其他选掼蛋课题的选手 PK；
3. 与已有掼蛋 AI 进行 PK；
4. 统计比赛结果，形成报告。

工程约束（PRD 提醒）：

- 自动跑对局的程序必须放到**独立线程**，不能卡 UI；
- **游戏逻辑与渲染严格分离**；
- 三人模块之间**低耦合**。

## 2. 算法方案调研与选型

### 2.1 候选方案对比

| 方案 | 代表工作 | 原理 | 效果 | 1 周可行性 |
|---|---|---|---|---|
| 深度强化学习 | DanZero / DanZero+（arXiv:2210.17087, 2312.02561） | 深度蒙特卡洛 + 分布式 Q-learning，神经网络 | 学界最强 | ❌ 需 GPU 集群 + 数周训练，排除 |
| 纯 MCTS/UCT | 多种牌类 AI | 蒙特卡洛树搜索 | DanZero 论文指出 UCT 版掼蛋 AI「仅略优于随机」：4 人、不完美信息、动作空间巨大导致模拟不可信 | ❌ 排除 |
| 纯规则启发式 | 工程界主流（记牌器、组牌辅助工具） | 手牌评估 + 人工牌理规则 | 强于随机，上限一般，策略写死后难调 | ⚠️ 可作基线 |
| **规则 + 末局搜索（混合）** | 斗地主 AI 的「猜牌采样 + minimax + alpha-beta」路线；**即 PRD 指定的分工方向** | 前中期规则决策；残局阶段对对手手牌采样后做完备/剪枝搜索 | 明显强于纯规则，工程量可控 | ✅ **采用** |

### 2.2 最终选型

**分层决策架构**：

- **前中期**：规则启发式。组牌（拆牌优化）+ 牌理策略（首发/跟牌/配合/炸弹时机/贡还牌）。
- **末局（残局）**：当各方剩余牌数低于阈值时，切换到搜索决策——基于记牌器推算剩余牌分布，对未知手牌做若干次**采样（假设完美信息）**，每次采样跑 **minimax + alpha-beta 剪枝**，投票选出最优动作。
- **记牌器与预测**：全程统计已出牌，维护剩余牌表；结合各家「PASS/不要」历史做排除法，估计炸弹概率与关键牌归属，供规则层和搜索层共用。

### 2.3 关键技术点

- **动作来源**：服务端每次下发 `actionList`，AI 只需输出**索引**（`actIndex`）。因此组牌/策略的输出必须**映射回 actionList 条目**，而不是自己造牌型——这是与示例代码对接的核心设计。
- **逢人配**：红桃级牌（heart rank card）可作万能牌，组牌枚举时需特殊处理（示例 `engine/` 中 `hearts_num` 逻辑可参考）。
- **还牌限制**：还贡牌点数不能大于 10（J/Q/K/A 非法），策略层需过滤。
- **线程模型**：Node 后端用 `worker_threads` 跑 AI 决策与批量对战，UI 进程只负责渲染与交互，满足 PRD 线程隔离要求。

## 3. 系统架构

```
┌─────────────────────────────────────────────┐
│  UI 前端（浏览器，渲染牌桌/控制自动跑/结果显示） │
└──────────────▲──────────────────────────────┘
               │ 本地 WebSocket / HTTP（状态推送）
┌──────────────┴──────────────────────────────┐
│  Node.js 后端（TypeScript）                   │
│  ├─ Client 层：连比赛服 ws://127.0.0.1:8181   │
│  │   建/入房、PLAY/TRIBUTE/PAYTRIBUTE 收发     │
│  ├─ State 层：消息 → GameState（本地局面重建） │
│  └─ AI 层（worker_threads，决策隔离）          │
│      ├─ Evaluator（牌力评估）    ── 成员 A    │
│      ├─ TributePolicy（贡还牌）  ── 成员 B    │
│      ├─ RulePolicy（组牌/牌理）   ── 成员 B    │
│      ├─ CardTracker（记牌/预测）  ── 成员 C    │
│      └─ EndgameSearch（采样+剪枝）── 成员 C    │
└─────────────────────────────────────────────┘
```

### 低耦合接口契约（开工前三人共同冻结）

```ts
// 唯一决策接口：输入局面 + 合法动作表，输出动作索引
interface Policy {
  chooseAction(state: GameState, actions: Action[]): number;
}

interface GameState {
  myPos: number;            // 我方座位 0-3
  handCards: string[];      // 我方手牌
  publicInfo: { rest: number }[]; // 各家剩余牌数
  selfRank: string; oppoRank: string; curRank: string;
  curPos: number; greaterPos: number;
  curAction: Action | null; greaterAction: Action | null;
  history: PlayRecord[];    // 本局全部出牌/PASS 历史（记牌器数据源）
  stage: 'play' | 'tribute' | 'back';
}

type Action = [string, string, string[]]; // [Pattern, Rank, CardList]
```

- 顶层 `RouterPolicy` 按阶段分发：进贡/还贡 → `TributePolicy`（B）；残局（如最大剩余牌数 ≤ N，N 可调）→ `EndgameSearch`（C）；其余 → `RulePolicy`（B）。`RulePolicy` 组牌选优与动作打分调用 `Evaluator`（A）；各策略均可只读访问 `CardTracker`（C）。
- 三人各自面向接口开发算法模块，互不依赖对方实现；公共数据结构（`GameState`、`Arrangement`、`Evaluator` 签名）在开工前冻结。

## 4. 三人分工

分工原则：**每人都负责"一块完整算法 + 与之衔接的工程"**，三人的算法模块均面向同一 `Policy` 接口开发、可独立测试。成员 A 因承担公共工程底座，算法模块体量相对较小但边界完整。

### 成员 A —— 工程底座 + 手牌分析与牌力评估

**工程部分**

| 职责 | 交付物 |
|---|---|
| WebSocket 客户端：协议收发、重连、多实例（4 个 AI 同房间） | `client/` 模块 |
| 游戏状态机：把服务端消息流重建为 `GameState`，维护出牌历史 | `state/` 模块 |
| UI：牌桌渲染（手牌/各家剩牌/当前出牌/级牌）、开始自动跑、速度调节、日志 | Web 前端页面 |
| 线程隔离：AI 决策与批量对战跑在 `worker_threads`，UI 不阻塞 | worker 框架 |
| 批量 PK 脚本：N 局自动对战，统计胜率/升级数/双下率，导出数据 | `bench/` 脚本 + 数据 |
| 集成联调、与已有 AI / 其他队伍 PK、汇总报告素材 | 报告数据章节 |

**算法部分**

| 职责 | 交付物 |
|---|---|
| 手牌分析与牌力评估：实现 `Evaluator`，从手数/单牌/炸弹/控制力四个维度给任意一种组法打分，供 B 的组牌选优与牌理打分调用 | `policy/evaluate.ts` |
| 评估权重调优：用批量对战数据回归调整四个维度的权重 | 调参记录 |

### 成员 B —— 组牌算法 / 出牌牌理（前中期策略）/ 贡还牌决策

| 职责 | 交付物 |
|---|---|
| 牌型识别：从手牌枚举所有合法牌型（含逢人配展开），定义公共 `Arrangement` 数据结构 | `policy/patterns.ts` |
| 组牌算法：枚举/DP 拆牌生成多种候选组法，调用 A 的 `Evaluator` 比选，目标最小手数、单牌 ≤3，输出映射到 actionList | `policy/arrange.ts` |
| 出牌牌理：首发策略、跟牌/垫牌策略、队友配合（送牌/接风/挡下家）、炸弹使用时机 | `policy/rule.ts`（实现 `RulePolicy`） |
| 贡还牌决策：实现 `TributePolicy`——进贡选牌（规则允许内损失最小）、还贡（≤10 过滤、不拆整牌、优先废单张）、抗贡识别 | `policy/tribute.ts` |
| 单元测试 + 与随机 bot 的胜率验证 | 测试与基线数据 |

### 成员 C —— 记牌器 / 手牌预测 / 末局剪枝搜索

| 职责 | 交付物 |
|---|---|
| 记牌器：108 张牌全量跟踪，剩余牌表、各点数剩余统计 | `search/tracker.ts`（实现 `CardTracker`） |
| 手牌预测：结合 PASS 历史做排除法，估计对手/队友持有炸弹与关键牌的概率 | `search/predict.ts` |
| 未知手牌采样器：按剩余牌分布生成合法对手手牌假设 | 并入 `search/endgame.ts` |
| 末局搜索：采样 + minimax + alpha-beta 剪枝（带深度/时间限制），多次采样投票 | `search/endgame.ts`（实现 `EndgameSearch`） |
| 残局触发阈值调参、搜索性能测试（单次决策耗时上限） | 参数与耗时报告 |

### 依赖关系

```
A 的 GameState 与全部接口（含 Evaluator 签名）开工前冻结 ──► 三人并行开发
A 的 Evaluator ──► 供 B 的组牌选优与牌理打分调用（先交付简单版，权重逐步迭代）
C 的 CardTracker ──► 供 A 评估、B 牌理只读访问（开工前约定字段）
A/B/C 各自的 Policy ──► A 在集成阶段统一集成进客户端与批量对战
```

## 5. 开发过程中新增与调整的逻辑

> 本节记录计划落地后的实际变更；与上文设想不一致处，以本节为准。

### 5.1 策略注册表（新增）

- 新增 `ai/policies.ts`：任何实现 `Policy` 接口的策略注册一个名字，即可被 bench / UI 的任意座位选用，算法与座位、工程完全解耦。
- 已注册策略（`ai/policies.ts` 现状）：`rule`（牌理 + 末局搜索，16 采样 / 0.8s）、`rule-ns`（纯牌理，无搜索）、`random`（随机基线）。

### 5.2 末局搜索迭代实录（重要调整，以本节为最新结论）

搜索从"净负收益"到"默认启用"经历四轮，全部经双方向换边对照裁决（逐场明细见 `doc/bench/`）：

**第 1 轮 · 初版（paranoid minimax + 随机采样）——净负**

- `rule` vs `rule-ns` 25 场 **0:25 全败**（0 胜的 95% 置信上界约 11%，排除运气）；对 random 含搜索版每场平均多拖 0.7 小局。判定：当前参数下搜索为净负收益。

**第 2 轮 · 内部 bug 修复 + 测量修正——仍负**

- 修复搜索内部 4 处 bug 并修正局级测量口径后仍未转正。

**第 3 轮 · 记牌器跨局修复 + 约束采样——翻正，搜索启用（转折点）**

- 根因：记牌器**从不跨局重置**——第 2 局起出牌记录错位、上一局打过的牌永远被当作未见牌，搜索一直在错误的牌池上采样（10 局一场的比赛 90% 的搜索输入是脏数据），这是"修完 bug 仍负收益"的残余主因。
- 新增 `search/constraints.ts`：从历史 PASS 推断各家持牌上限（对**对手**的单/对/三 PASS → 无更大同类天然牌型；对炸 PASS → 无更大天然炸；队友领先让牌无信息；该家之后打出矛盾牌则推断自洽作废），采样最多重试 40 次取零违约分法，约束互斥时取违约最少。
- 实测（32 场 / 390 局）：**局 51.0%、场 19:13**，对比修复前 44.9% / 5:11 翻正。场胜率提升比局胜率更明显，符合"搜索价值集中在决定比赛的残局关键手"的机制。`rule` 自此恢复含搜索。

**第 4 轮 · 拟人 rollout 重写 + 复杂度回退——持平保留，默认启用**

- 推算引擎由 minimax + alpha-beta 改为 **PIMC 拟人 rollout**：每个座位从自视角用牌理同款评分器 `scorePlayAction`（含让队友/拦截/救炸修正）选招推演到底——旧 paranoid 假设等于"对手透视我手牌打最坏情况"，是系统性悲观偏差；rollout 消的是偏差而非噪声，单次成本 O(步数)，同预算样本数多一个数量级（实测 4 样本 × 3 候选约 18ms）。
- 顺带修复 `payoff` 末游计分：推算在 3 家出完时停止，第 4 名不在名次表中，原实现把"头游+末游=1 分"错算成 0。
- 实测（32 场 / 414 局）：**局 48.3%、场 17:15**，与第 3 轮版本统计上不可区分；因模型更干净、速度更快而保留。
- 同日验证了三项候选增强均无实测增益（顺子类进模拟器、贡还牌必持硬约束、采样数 16→32），按"无收益不留复杂度"原则移除（约 130 行）；采样数维持 16。

**最终架构**：约束采样（PASS 推断过滤）→ 拟人 rollout 推演 → 平均收益定案（候选预筛前 6、覆盖裕度 25、有效样本 <4 回退牌理）。`rule` = 牌理 + 末局搜索（16 采样 / 0.8s），`rule-ns` = 纯牌理对照。

**安全网（全程保留）**：候选动作用牌理评分预筛（跟牌时 PASS 强制保留）；搜索均值超过牌理首选 25 分（`overrideMargin`）才允许覆盖；样本不足直接回退牌理——保证搜索只可能在有把握时改变决策。

**已验证影响有限的简化假设**：模拟器不生成顺子类长牌型、逢人配按原点数参与（第 4 轮实测剔除）；收益 `payoff` 只看最终名次（双下 3 / 头游+三游 2 / 头游+末游 1，×100），不计升级级数。

**实现相对原计划的调整**：采样器并入 `search/endgame.ts`（不单列 `search/sample.ts`）；多次采样按**平均收益**定案（原计划为投票）；推演由计划的 minimax + alpha-beta 改为拟人 rollout；类默认参数 24 采样基数（未见牌 ≤12 翻倍、≤20 ×1.5）/ 候选 6 / 步数兜底 100 / 时限 1.5s / 覆盖裕度 25。

### 5.3 评估权重调参落地

- 坐标上升法自动调参：调后权重与旧默认权重直接对战 20:0，新权重已固化到 `types.ts`，原始记录存于 `bench/tuned-weights.json`。

### 5.4 工程新增

- 离线冒烟测试 `src/smoke.ts`（`npm run smoke`）：24 项断言覆盖状态机、组牌、评估、记牌、约束采样、末局搜索与整体流程，末局单次决策实测约 30ms。
- UI 广播架构：AI 对战在 worker 线程中推进，每一步事件广播给全部页面渲染；日志设 2000 条上限，防止长时间对战卡顿。
- 基线结论：`rule` / `rule-ns` 对 `random` 换边对照各 40:0（100%），规则基线有效；逐场明细落盘 `doc/bench/`，服务端累计统计见 `OpenGuanDan/log.txt`（截至 2026-10-21：543 场 / 4845 小局 / 54.9 万条交互，可作报告的实验规模佐证）。

### 5.5 UI 计分修复：场边界探测（2026-10-21）

- 问题：牌桌记分板"大局"不更新、"本场"跨场累加（曾出现 62:27）、日志"末场胜局"恒为 0:0。
- 根因：服务端 `gameOver` 通知实测只在**全部场次打完时**到达一次（OpenGuanDan README 4.1.7 协议中该消息亦无 `victory` 字段）；原实现依赖逐场收到 `gameOver` 来入账大局 / 清零本场，因此全部失效，结果兜底还会把最后一场重复入账。
- 修复（`ui/aiWorker.ts`）：利用"一场之内双方等级只升不降、新一场双方回 2"的规律，在每局首个动作处探测**任一队等级回退**作为场边界——逐场入账大局（胜方 = 末局头游队，过 A 必为末局头游队）、清零本场、局号从 1 重计；两队等级交错重置时用屏蔽标志防重复探测；`gameOver` 仅补记最后一场（`gameCount < rounds` 守卫）；`lastScore` 快照解决"末场胜局 0:0"。
- 附带：全部对局日志持久化到 `logs/games.log`（`ui/server.ts`），可用于复盘与报告素材。
